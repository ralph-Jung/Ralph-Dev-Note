## ① 큰 그림 (지도)

이 노트가 서는 위치 — 3층 중 맨 아래다.

```
[자바 언어 자체]     → [[JavaBasics]]
[영속성 계층 JPA]    → [[Persistence]]     ← 자바에서 본 DB
[DB 자체]            → 이 노트             ← SQL · 스키마 · 제약 · 마이그레이션
```

**스키마를 코드로 관리하는 두 패러다임** — 어느 쪽을 골랐는지가 나머지 규칙을 전부 결정한다.

```
명령형 / 시간축   변경 단계를 "순서대로 쌓는다"         Flyway, Liquibase
                  → 과거 파일은 못 고침, 새 버전을 추가

선언형 / 공간축   "최종 스키마"를 선언하면 도구가 diff   Atlas, Skeema, ddl-auto=update
                  → 버전 번호도 이력 테이블도 없음
```

이 프로젝트는 `ddl-auto=update`(선언형)에서 **Flyway + `validate`(명령형)** 로 옮겼다. 즉 "내가 순서대로 적는다"를 택했다.

**Flyway가 부팅 때 하는 일은 세 단계로 분리돼 있다.**

```
① 스캔    파일을 전부 텍스트로 읽어 CRC32 계산      ← SQL 실행 없음
② 검증    이력 테이블과 대조 → 불일치면 전체 중단
③ 실행    이력에 없는 버전만 SQL 실행 + 이력 기록
```

단계마다 대상이 다르다 — ①은 **모든** 파일, ②는 **이미 적용된** 것, ③은 **아직 안 된** 것.

## ② 질문 트리 (본문)

### 2026-07-24

#### Q. Flyway는 시간축에 초점을 맞춘 건가? 나는 공간축(마이그레이션 파일로 새 DB에 같은 스키마를 재현)으로 생각했는데?
- **한줄답**: 둘 다 되지만 대등하지 않다. ==공간축은 시간축의 따름정리==다. 설계 중심은 시간축이고 공간 재현은 그 부산물이다.
- **원리**: `flyway_schema_history` 테이블이 답이다. 기록하는 건 `installed_rank`(순서)·`version`·`checksum`·`installed_on`뿐이고 ==현재 스키마가 어떻게 생겼는지를 담은 컬럼이 하나도 없다.== Flyway는 스키마의 *상태*를 모르고 *진행도*만 안다.

  시간축이 설계 중심인 증거 셋:
  1. **파일명의 버전 번호가 정체성** — `V2__add_problem_domain.sql`에서 의미를 갖는 건 내용이 아니라 `2`라는 순서
  2. **체크섬으로 과거 수정을 금지** — 순수 공간축 도구라면 최종 스키마만 맞으면 되니 파일을 고쳐도 상관없어야 한다. 막는다는 건 "지나간 시점은 못 바꾼다"를 강제한다는 뜻
  3. `baseline`, `repair` 같은 명령이 전부 **타임라인 위의 위치**를 다룬다

  "순서가 있고 변하지 않는 시퀀스 + 어디까지 적용했는지 기록"이라는 **하나의 성질**에서 둘이 동시에 나온다.

```
시간축   기존 DB 를 V2 → V3 로 전진
공간축   빈 DB 에 V1 부터 V3 까지 몰아서 적용 → 같은 스키마
```

  공간축이 성립하는 이유가 시간축을 엄격히 통제했기 때문이라, 인과가 한 방향이다.

  **다만 공간 재현은 저절로 유지되지 않는다.** ① `V1`부터 전부 남아 있고 ② 마이그레이션이 결정적이고(`now()`나 환경 의존 값이 스키마 정의에 끼면 안 됨) ③ **그 경로를 실제로 돌려봐야** 한다. 평소엔 기존 DB를 전진시키기만 하니 "빈 DB에서 처음부터 재생"은 아무도 안 밟고, 신규 세팅이나 CI가 새 DB를 만들 때 **몇 달 전에 깨진 게 그제야 드러난다.**
- **연결**: → 아래 Q(파일을 실행해보고 비교하나?), JPA 쪽 스키마 검증(`ddl-auto=validate`)은 → [[Persistence]]

#### Q. 그러면 모든 파일을 실행해보고, 이전 버전은 DB의 체크섬과 비교해서 같으면 다음 파일을 실행하고, 틀리면 거기서 멈추는 건가?
- **한줄답**: 두 군데가 다르다. ① ==체크섬은 실행이 아니라 파일을 텍스트로 읽어서 계산==한다. ② ==검증을 전부 끝낸 다음에 실행이 시작된다== — 파일마다 교대로 돌지 않는다.
- **원리**:

  **① 실행이 아니라 읽기다.** SQL을 돌려보고 결과를 비교하는 게 아니라 파일의 글자를 읽어 CRC32를 낸다. DB에 연결할 필요도 없는 순수한 문자열 계산이라, 파일이 `CREATE TABLE`이든 아무 의미 없는 글자든 값은 나온다.

  그리고 ==체크섬은 파일 어디에도 없다.== 저장되는 곳은 `flyway_schema_history.checksum` 한 곳뿐이고, 파일 쪽은 매번 즉석에서 계산한다. 즉 비교는 **계산값 vs 저장값**이다.

```
[디스크의 파일]                        [DB 이력 테이블]
V2__add_problem_domain.sql              version  = 2
   ↓ 글자를 읽어 CRC32 계산              checksum = 925344562
 925344562        ←── 같은가? ──→       925344562        통과
```

  이 구조라서 위조가 안 된다. 체크섬이 파일에 *적혀 있는* 값이면 파일을 고치며 같이 고치면 그만이지만, **파일에서 유도되는 값**이라 손댈 자리가 없다. `repair`가 따로 있는 이유도 DB 쪽 값을 바꾸는 것 말고는 방법이 없어서다.

  **② 검증과 실행은 교대로 돌지 않는다.**

```
[교대라면 — 실제로는 이렇지 않음]
V1 검증 → 통과 → V1 실행
V2 검증 → 통과 → V2 실행
V3 검증 → 실패 → 멈춤          ← V1, V2 는 이미 실행돼 버림

[실제 — 검증을 전부 먼저]
V1 검증 ┐
V2 검증 ├─ 전부 대조 → 하나라도 불일치면 아무것도 실행하지 않고 중단
V3 검증 ┘
   ↓ 전부 통과했을 때만
아직 적용 안 된 것만 실행
```

  전부 먼저 검증하면 실패 시점에 **아직 아무것도 안 건드린 상태**라 롤백할 것도 없다. 교대였다면 앞부분만 적용된 어중간한 스키마가 남는다.

  **"이력에 있으면 실행 안 한다"와 "매번 파일을 읽는다"는 동시에 성립한다** — 거르는 건 실행 여부뿐이고, 읽고 검증하는 건 항상 전부다. 애초에 안 읽으면 수정됐는지 알 방법이 없다.

| 단계 | 대상 | SQL 실행 |
|---|---|---|
| ① 스캔 | **모든** 파일 | 없음 |
| ② 검증 | **이미 적용된** 것만 (이력에 짝이 있는 것) | 없음 |
| ③ 실행 | **아직 적용 안 된** 것만 | 있음 |

  그래서 적용된 `V2`를 고치면 **전체가 막힌다.** 멀쩡한 `V3`도 적용 안 되고 애플리케이션 자체가 부팅 실패한다(`FlywayValidateException`). 복구는 **파일을 되돌리거나 / 새 `V3`를 추가**하는 게 정석이고, `flyway repair`는 DB가 아니라 **이력의 체크섬만** 덮어써서 "파일 ≠ 실제 DB"를 조용히 만드는 최후 수단이다.
- **연결**: → 위 Q(시간축인가 공간축인가?)

## ③ 용어 카드 (역참조)

> [!quote]- 용어 6개
> - **flyway_schema_history**: Flyway가 만드는 이력 테이블. `installed_rank`·`version`·`checksum`·`success`·`installed_on`을 기록한다. **현재 스키마 상태는 담지 않는다** — 진행도만 안다. → Q(시간축인가?)
> - **체크섬 (CRC32)**: 마이그레이션 파일 내용으로 계산하는 정수. 파일에는 없고 이력 테이블에만 저장되며, 부팅마다 재계산해 대조한다. → Q(실행해보고 비교하나?)
> - **validateOnMigrate**: 기본 `true`. migrate 전에 검증이 먼저 돈다. 그래서 불일치 시 SQL이 한 줄도 안 나간다. → Q(실행해보고 비교하나?)
> - **flyway repair**: 이력의 체크섬을 현재 파일 값으로 덮어쓰는 명령. DB 스키마는 안 바꾸므로 "파일 ≠ 실제 DB"를 조용히 만든다. 최후 수단. → Q(실행해보고 비교하나?)
> - **명령형 마이그레이션 (시간축)**: 변경 단계를 순서대로 쌓는 방식. Flyway, Liquibase. 과거 파일 수정 금지. → ① 큰 그림
> - **선언형 마이그레이션 (공간축)**: 최종 스키마를 선언하면 도구가 diff를 계산. Atlas, Skeema, `ddl-auto=update`. 버전 번호·이력 테이블이 없다. → ① 큰 그림
